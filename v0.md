## � Product Purpose: Prosthetic for Executive Dysfunction

**Core Insight:** This is not a productivity app. It's a **prosthetic for executive dysfunction**, specifically designed to augment the prefrontal cortex functions impaired in ADHD.

### The 6 Executive Function Domains We Scaffold:

1. **Organizing, Prioritizing, & Activating to Work**
   - Agent does: Morning brain dump → prioritization → timeblocking
   - Externalizes: Task breakdown, sequencing, first-step identification

2. **Focusing, Sustaining, & Shifting Attention to Task**
   - Agent does: Task initiation prompts ("Time to start X. What's the first 2-min step?")
   - Externalizes: Attention anchoring, transition support

3. **Regulating Alertness, Sustaining Effort, & Processing Speed**
   - Agent does: Energy-aware scheduling, break reminders, pacing checks
   - Externalizes: Effort regulation, rest periods

4. **Managing Frustration & Modulating Emotions**
   - Agent does: "What's blocking you?" on stuck status, non-judgmental check-ins
   - Externalizes: Emotional regulation through conversation

5. **Utilizing Working Memory & Accessing Recall**
   - Agent does: Persistent session state, recall of today's tasks, carryover management
   - Externalizes: Memory of plan, progress, context

6. **Monitoring & Self-Regulating Action**
   - Agent does: Check-ins at block ends, dynamic replanning, evening reflection
   - Externalizes: Progress tracking, course correction

**Key Principle:** The agent is **not** just checking in at task end. It scaffolds **before** (initiation), **during** (sustaining) like pomodoro, and **after** (reflection) every task block. This is comprehensive executive function augmentation.

### Reverse Engineering Executive Functions

From clinical research (Barkley, 2011):
- **Externalize time**: Visual calendars, explicit time remaining ("4 hours left before bedtime")
- **Break up lengthy tasks**: "What's the first 2-minute step?"
- **Externalize motivation**: Positive reinforcement, progress visualization
- **Externalize problem-solving**: Agent offers replan options when stuck
- **Replenish SR Resource Pool (Willpower)**: Scheduled breaks, meal anchors, sleep prep

**v0 Focus:** Static preferences (wake_time, health_anchors). Agent applies these rules proactively.
**v1 Adds:** Agent learns user's patterns (when they get stuck, what helps, personal triggers) and adapts scaffolding.

@tool

**NEW (RIGHT - returns to agent thread):**
```python
@tool
def set_checkin_timer(duration_minutes: int, reason: str) -> dict:
    """
    Agent sets its own timer.  
    Returns action that causes agent thread to sleep.
    """
    resume_time = datetime.now() + timedelta(minutes=duration_minutes)
    
    # Save to session for context
    update_session(session_id, {
        'next_checkin': resume_time.isoformat(),
        'checkin_reason': reason
    })
    
    # Return to agent - thread will sleep
    return {
        'action': 'WAIT',
        'duration_minutes': duration_minutes,
        'reason': reason,
        'resume_at': resume_time.strftime('%I:%M %p')
    }

**The vision:**

Like Cursor/Antigravity IDE coding agent:

    ↓ LLM has context from morning planning
- 2 PM: Check-in

# agent/session_manager.py
from google.adk.sessions import InMemorySessionService
from agent.repos import session_repo

# ADK session stays in RAM
session_service = InMemorySessionService()

async def save_agent_session_to_db(session_id: str, state: dict):
    """Sync ADK session state to SQLite after each turn."""
    await session_repo.upsert_session(
        session_id=session_id,
        state_json=json.dumps(state),
        updated_at=datetime.utcnow()
    )

async def restore_session_from_db(session_id: str) -> dict:
    """Restore session state from SQLite on server restart."""
    db_session = await session_repo.get_session(session_id)
    if db_session:
        return json.loads(db_session.state_json)
    return {}


async def create_daily_session(user_id: str) -> Session:
    """Create new ADK session at wake time (8 AM)."""
    session = await session_service.create_session(
        user_id=user_id,
        app_name="intentive",
        initial_state={
            'date': date.today().isoformat(),
            'wake_time': get_wake_time(user_id),
            'calendar': await get_calendar_events(user_id),
            'tasks': await get_open_tasks(user_id)
        }
    )
    return session

async def get_or_create_session(user_id: str) -> Session:
    """Get today's session or create if doesn't exist."""
    active_session = await session_service.get_active_session(
        user_id=user_id,
        app_name="intentive"
    )
    
    if not active_session or active_session.state.get('date') != date.today().isoformat():
        # New day, create new session
        return await create_daily_session(user_id)
    
    return active_session
```

### 4. Session Context Management

```python
def format_adk_session_context(session: Session) -> str:
    """Format ADK session state for injection into Live/Standard API."""
    state = session.state
    
    return f"""
TODAY: {state.get('date')}
CURRENT TIME: {datetime.now(pytz.timezone(state.get('timezone', 'UTC'))).strftime('%I:%M %p')}

PLANNED SCHEDULE:
{format_calendar_events(state.get('calendar', []))}

ACTIVE TASKS:
{format_tasks(state.get('tasks', []))}

SESSION PROGRESS:
- Started: {state.get('wake_time')}
- Completed blocks: {len([h for h in state.get('history', []) if h.get('type') == 'checkin'])}
- Next check-in: {state.get('next_checkin')}

"""

async def update_adk_session(session_id: str, updates: dict):
    """Update ADK session after each interaction."""
    session = await session_service.get_session(session_id)
    
    # Append to history
    history = session.state.get('history', [])
    history.append({
        'timestamp': datetime.now().isoformat(),
        **updates
    })
    
    # Update state
    session.state['history'] = history
    session.state['last_updated'] = datetime.now().isoformat()
    
    await session_service.update_session(session)
```

## 🧠 The "Machine That Builds The Machine" Concept — **v1 Vision**

> **⚠️ This entire section describes v1 functionality.** v0 uses static preferences only.

**From ChatGPT conversation - Elon's principle applied:**

> "Don't build the machine, build the machine that **builds** the machine."

We're not building fixed policies. We're building **a system that generates policies on demand**.

### Traditional Approach (WRONG - Too Robotic):

```python
# Hardcoded policy
if notifications_ignored >= 3:
    escalate_to_call()
```

This is a "machine" - rigid, pre-defined, same for all users.

### Our Approach (RIGHT - Adaptive Playbook Builder):

```python
# Playbook is learned, not hardcoded
playbook = {
    "morning_responsiveness": {
        "push_response_rate": 0.85,  # User opens 85% of morning notifications
        "best_time_window": "8:00-8:15 AM",
        "effective_phrasing": "Ready to plan?" vs "Time to start"
    },
    "afternoon_drift_risk": {
        "high_risk_window": "2:00-4:00 PM",  # User often derails here
        "intervention": "increase_check_in_frequency",
        "anchor_protection": ["lunch", "3pm coffee"]
    },
    "granularity_spectrum": 67,  # Not LOW/MED/HIGH - exact learned value (0-100)
    "task_initiation_friction": {
        "pattern": "struggles_with_first_step",
        "effective_prompt": "What's the 2-min action?" > "Start now"
    }
}
```

**How the agent BUILDS this playbook:**

```python
# After each interaction, agent updates its own playbook
@after_checkin
def update_playbook(user_id, interaction_data):
    # Did notification work?
    if interaction_data['notification_opened_within_5min']:
        increment_success('push_notifications', context=time_of_day)
    else:
        # Build new strategy on demand
        if get_pattern('push_failures_consecutive') >= 2:
            # Agent decides: "This user needs calls in afternoons"
            add_playbook_rule(user_id, {
                'afternoon_channel': 'call',  # Learned, not hardcoded
                'rationale': 'Push ignored 2x, user responsive to calls'
            })
```

**This is NOT stored as "if-then rules" but as learned patterns:**
- Agent observes: "User clicks 85% of morning notifications" → trust push in AM
- Agent observes: "User ignores afternoon push" → adapt strategy (try different phrasing, time, or escalate to call when available)
- Agent observes: "Task overruns happen at 2 PM" → proactively check-in earlier before 2 PM tasks

**Hyper-personalization:**
- NOT "1 million users in 3 categories (LOW/MED/HIGH)"
- BUT "1 million users = 1 million unique playbooks"
- Each playbook is a spectrum, not a bucket
- Example: `granularity_spectrum: 67` means this specific user needs check-ins every 48 minutes (not 30, not 60 - exactly 48)

**This is a v1 feature** - v0 uses static preferences only. The above playbook learning concept will be implemented post-launch.

from agent.database import get_db, AsyncSession
from agent.models import ScheduledEvent

async def create_event(
    user_id: str,
    event_type: str,
    event_time: datetime,
    metadata: dict = None
) -> str:
    """Create a scheduled event."""
    async with get_db() as db:
        event = ScheduledEvent(
            id=str(uuid.uuid4()),
            user_id=user_id,
            event_type=event_type,
            scheduled_time=event_time.isoformat(),
            metadata=json.dumps(metadata or {}),
            status='pending'
        )
        db.add(event)
        await db.commit()
        return event.id

async def get_pending_events() -> list:
    """Get all pending events that should execute now."""
    async with get_db() as db:
        now = datetime.utcnow()
        events = await db.execute(
            select(ScheduledEvent)
            .where(
                ScheduledEvent.status == 'pending',
                ScheduledEvent.scheduled_time <= now.isoformat()
            )
        )
        return events.scalars().all()

@app.post("/api/check-pending")
async def check_pending_events(x_cron_secret: str = Header(None)):
    """External cron hits this every minute."""
    
    # Simple auth
    if x_cron_secret != os.getenv("CRON_SECRET"):
        raise HTTPException(status_code=401)
    
    # Get pending events
    events = await event_repo.get_pending_events()
    
    executed = []
    for event in events:
        try:
            # Execute event
            if event.event_type == 'morning_wake':
                await handle_morning_wake(event.user_id)
            elif event.event_type == 'checkin':
                metadata = json.loads(event.metadata)
                await handle_checkin(event.user_id, metadata.get('reason'))
            elif event.event_type == 'start_block':
                metadata = json.loads(event.metadata)
                await handle_start_block(event.user_id, metadata.get('block_name'))
            
            # Mark as completed
            await event_repo.update_event_status(event.id, 'completed')
            executed.append(event.id)
        except Exception as e:
            logger.error(f"Failed to execute event {event.id}: {e}")
            await event_repo.update_event_status(event.id, 'failed')
    
    return {'executed': executed, 'count': len(executed)}

## Error Handling Strategy

### Critical Failure Modes & Recovery

---

#### 1. **Scheduler Job Loss (Server Restart)**

**Symptoms:**
- Server restarts mid-day
- All check-in timers disappear
- User isn't prompted anymore

**Prevention:**
```python
# agent/database.py - Always persist next_checkin to DB
def update_session_next_checkin(session_id: str, next_time: datetime):
    with db.session() as sess:
        sess.query(Session).filter_by(id=session_id).update({
            'next_checkin': next_time
        })
        sess.commit()

# agent/scheduler_service.py - Rebuild on startup
def ensure_daily_schedules():
    """Called on server startup to ensure wake events exist"""
    today = date.today()
    users = get_all_users()
    
    for user in users:
        # If no morning wake event exists for today, create one
        if not event_repo.get_event(user.user_id, 'morning_wake', today):
            wake_time = datetime.combine(today, user.wake_time)
            event_repo.create_event(user.user_id, 'morning_wake', wake_time)
```

**Recovery:** On server start, check all `EXECUTING` state sessions and restore their timers. Fire missed check-ins immediately.

---

#### 2. **Database Connection Drop Mid-Session**

**Symptoms:**
- Tool calls fail with DB timeout
- Session state not persisting
- Agent can't read user preferences

**Mitigation:**
```python
# agent/database.py
from sqlalchemy.exc import OperationalError
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10)
)
def get_session(session_id: str):
    try:
        with db.session() as sess:
            return sess.query(Session).filter_by(id=session_id).first()
    except OperationalError as e:
        logger.error(f\"DB connection failed: {e}\")
        raise  # Trigger retry

# If all retries fail, agent continues with in-memory state (degraded mode)
```

**Degraded Mode:** If DB is completely down, agent runs in-memory only (like old MVP) and logs warning. User sees "Some features unavailable" message.

### Decision Context: Internal vs External Timer

| Feature | External Timer (Selected) | Internal Timer (`asyncio.sleep`) |
|---------|---------------------------|----------------------------------|
| **Serverless Compatible** | ✅ Works on Render/Cloud Run free tier | ❌ Requires always-on ($7-10/mo) |
| **Agent Autonomy** | ✅ Agent decides times, saves to DB | ✅ Agent decides times directly |
| **Cost at Scale** | ✅ Optimized (pay per execution) | ❌ High (pay for idle time) |
| **Multi-Agent Ready** | ✅ Each agent schedules independently | ⚠️ Thread management complexity |
| **Complexity** | Medium (external cron setup) | Low (single process) |

**Why we chose External Timer for v0:**
- **Free Tier Compatibility**: Render/Cloud Run free tiers scale to zero. External cron wakes them only when needed.
- **Future-Proof**: This architecture works at every scale (v0 single user → v1 Cloud Run → v2 multi-agent).
- **Cost Optimization**: At scale, paying for idle compute (internal timer) is wasteful. External execution is pay-per-use.
- **Agent Still Decides**: The agent calls `set_checkin_timer()` and decides its own schedule. External cron just executes what the agent decided.

You are asking: "Why do we need a dumb cron job that hits every minute? Why can't the agent just set a specific timer for 3:00 PM and wake up exactly then?"

The answer is: Server limitations.

The Problem: Your Server is a Comatose Patient
When you host a Python script on a cloud server (like Render, Heroku, or AWS Lambda), it doesn't "stay awake" like your laptop.

It freezes: If no one talks to it, the server puts the process to sleep to save money.
It restarts: Cloud providers randomly restart servers for maintenance.
It forgets: If you use time.sleep(9000), and the server restarts, that sleep is cancelled and the agent never wakes up.
The Solution: The "Alarm Clock" Pattern
We need an external reliability mechanism.

Option A: The "Polling" Method (Current Plan)

Mechanism: A free service (cron-job.org) pokes your server every minute: "Anything to do now? Anything to do now?"
Pros: Extremely reliable, free, works on any server.
Cons: Feels "dumb" to have a heartbeat every minute.
Option B: The "Targeted Trigger" Method (What you are asking for)

Mechanism: When the agent says set_timer(90 mins), the code dynamically creates a one-time scheduled job in an external system (like Google Cloud Tasks or a specialized scheduler) to hit the server exactly in 90 minutes.
Pros: Elegant, precise.
Cons: Crucially, this requires setting up a separate infrastructure (Redis, Celery, or Cloud Tasks) which is overkill for "v0". It adds $10-20/month or complex configuration.
Why "v0" uses Option A
For a "v0" prototype, we use Option A because it simulates Option B perfectly to the user, but costs $0 and takes 5 minutes to set up.

To you (the developer) and the user, the Agent is setting its own timer.
The Agent says: "Wake me up at 3:00 PM."
The Infrastructure (Cron) checks the clock every minute.
At 2:59 PM: Cron asks "Time yet?" -> DB says "No."
At 3:00 PM: Cron asks "Time yet?" -> DB says "Yes! Wake up the agent!"

1. What "External Service" are we using for v0?
We are using cron-job.org (or similar Simple Cron).

Capabilities: It can hit a URL at fixed intervals (e.g., every 1 min, every 5 mins).
Limitations: It CANNOT accept dynamic requests like: "Hit this URL once at 3:14 PM."
So, when the Agent says set_timer(45 mins), we cannot tell cron-job.org: "Hey, wake me up in 45 mins." It doesn't have an API for that.

2. So where does the timer live?
Because the external service is "dumb" (fixed interval), the intelligence (the specific 3:14 PM wake-up time) must live in Our Database (SQLite).

Agent: "Wake me up at 3:14 PM." -> Saves 3:14 PM to DB.
External Service: "Is it time? (2:59)" -> DB says No, sleep.
External Service: "Is it time? (3:00)" -> DB says No, sleep.
...
External Service: "Is it time? (3:14)" -> DB says YES! -> Server wakes up.
3. Why Redis/Cloud Tasks (v1)?
These are different kinds of external services.

Cloud Tasks Capabilities: It CAN accept dynamic requests: "Hit this URL once at 3:14 PM."
But: Setting this up requires Infrastructure Code (IAM roles, service accounts, queue configuration), which is overkill for a prototype.
Summary
v0 (Current Plan): "External Timer" = Our Data + Dumb External Poller.
Pro: Dead simple, free, works on any server.
Con: High latency (up to 59s).
v1 (Future): "External Timer" = Smart External Trigger Service.
Pro: Precise, no wasted checks.
Con: Complex setup (Cloud Console, etc.).

v0: The "Alarm Clock" (Poll-Based) — Current
Mechanism: A dumb cron job checks every 1 minute: "Is it time?"
Pros: Easy, free, works on any server.

#### CORE Design Principle: NO Classification - EVER

1. **Humans don't think in buckets**: "Work" for a startup founder coding = different from "work" for consultant in client meeting. Both are "work" but require completely different scaffolding.

The "Startup Logic" is purely a safety net to keep the heart beating. Here is the breakdown:

1. The "Heartbeat" (Why we need Startup Logic)
Imagine this scenario:

Today at 10:00 PM: You and the Agent finish your day. The Agent reflects and says goodnight.
Tonight at 3:00 AM: The server hosting the Agent (Render) restarts automatically for an update, or crashes and reboots.
Tomorrow at 8:00 AM: ...Silence.
Why silence? Because if the Agent was supposed to schedule "Tomorrow's Wake Up" at the end of "Today's Session," but the server crashed or the logic failed, then nothing is scheduled. The chain is broken.

The Startup Logic fixes this: Every time the server turns on (restarts), it immediately checks: "Does User Srujan have a wake-up call scheduled for tomorrow morning?"

If YES: Great, do nothing.
If NO: Panic! Create one immediately so he isn't left alone tomorrow.
This guarantees that no matter how many times the server crashes or restarts, the Continuity of the daily cycle is preserved.

2. Idempotency (Preventing Duplicates)
Since the server might restart 10 times a day (during development), we don't want 10 wake-up calls. Idempotent just means: "Check if it exists first. If it exists, skip it." This ensures exactly one wake-up call per day, regardless of how many times I deploy code.

3. The Memory Model (Day vs. Forever)
You are exactly right about the memory:

Within the Day (Continuity): From 8:00 AM to 10:00 PM, the Agent remembers everything. This is the "Thread." If you tell it at 9 AM that you are tired, and at 3 PM you try to book a heavy workout, it remembers and says "Hey, you said you were tired this morning."
Tomorrow Morning (The Reset): At 10:00 PM, the session ends. At 8:00 AM tomorrow, a new session starts. In v0: This is a blank slate. It does not remember yesterday. It's a fresh start. In v1: We will add "Long Term Memory" so it can look back at yesterday, but for now, you are correct—it recycles.
Summary: The "Startup Logic" is just the engineering glue that makes sure the "Fresh Start" actually happens every morning, even if the world falls apart overnight.
